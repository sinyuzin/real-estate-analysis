# 국토교통부 아파트 매매 실거래가 — 수집과 집계

공공데이터포털의 아파트 매매 실거래 신고자료를 받아 단지·구·월 단위로
집계하는 스크립트다. 서울 다섯 개 구, 3년치를 기본값으로 두었다.

파일은 [`molit_screening.py`](molit_screening.py) 하나다.

## 하는 일

수집과 집계를 한 덩어리로 두지 않고 세 단계로 끊었다.

```
collect()  ──▶  tidy()  ──▶  summarize_*()
  API          한 건 = 한 행        집계
   │               │                │
00_raw_api.csv  01_deals.csv   02~05_*.csv
```

단계마다 CSV를 떨군다. 개발계정은 일일 호출 한도가 있어서, 집계 방식을
고칠 때마다 API를 다시 부르면 금방 한도를 넘는다. `01_deals.csv`를 읽어
`summarize_*()`만 다시 호출하면 API 없이 집계를 고칠 수 있다.

## 실행

```bash
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
export MOLIT_KEY="발급받은_인증키"                    # Windows: set MOLIT_KEY=...
python molit_screening.py
```

인증키는 [공공데이터포털](https://www.data.go.kr)에서 「국토교통부_아파트
매매 실거래가 자료」 활용신청을 하면 받는다. Encoding 키든 Decoding 키든
어느 쪽을 넣어도 된다. 아래 [인증키](#인증키) 항목 참고.

조회 범위는 파일 위쪽 상수로 바꾼다.

```python
REGIONS = {"11680": "강남구", ...}   # 법정동코드 5자리
YEARS_BACK = 3                        # 몇 년치
MIN_DEALS = 10                        # 단지별 집계 최소 거래건수
```

## 집계에서 쓰는 지표

**평당가.** 같은 단지라도 20평과 40평은 총액이 다르다. 단위면적당으로
맞추지 않으면 면적 차이를 가격 차이로 읽게 된다.

**가격변동계수.** 같은 단지·같은 면적대 안에서 평당가가 흩어진 정도를
표준편차가 아니라 평균 대비 비율로 잰다. 표준편차는 단위가 붙어 있어
비싼 단지가 무조건 커 보인다. 평균으로 나누면 40억 단지와 15억 단지를
같은 잣대로 비교할 수 있다.

**층 보정 후 잔여 분산.** 단지·면적대 안에서 평당가를 층에 대해 1차
회귀시키고, 회귀선으로 설명되지 않는 부분의 흩어짐을 다시 잰다.

```
평당가 = a × 층 + b + 잔차
```

`cv_resid`가 `cv_raw`와 비슷하면 층으로 설명되지 않는 흩어짐이 크다는
뜻이고, 많이 줄어들면 그 단지의 가격차가 대부분 층 차이였다는 뜻이다.
`r2`는 층이 평당가 변동의 몇 %를 설명하는지다. 회귀는 단순 분산보다
표본이 더 필요해서 최소 표본을 20건으로 잡았다. 점 다섯 개로 직선을
그으면 기울기가 우연에 크게 흔들린다.

향·타입·수리 상태는 실거래 자료에 없어 보정할 수 없다. 여기서 걷어내는
것은 층 하나뿐이다.

## 이 API를 다루며 부딪힌 것

남이 같은 데서 시간을 버리지 않도록 적어둔다. 자세한 경위는 코드 주석에
있다.

**인증키가 이중 인코딩된다.** 포털은 같은 키를 Decoding(원본)과
Encoding(URL 인코딩) 두 형태로 준다. Encoding 키를 `requests`의
`params=` 딕셔너리로 넘기면 `requests`가 한 번 더 인코딩해서 `%2F`가
`%252F`가 되고, 서버가 키를 못 알아봐 403이 난다. `build_url()`은 키에
`%`가 있으면 이미 인코딩된 것으로 보고 그대로 두고, 없으면 한 번만
인코딩해 URL을 직접 조립한다.

**엔드포인트가 두 개다.** `RTMSDataSvcAptTradeDev`와
`RTMSDataSvcAptTrade`가 나란히 있고, 첨부 기술문서에 적힌 주소와 내
마이페이지에 표시되는 주소가 다를 수 있다. `diagnose()`가 엔드포인트
두 종 × 키 형태 두 종을 전부 찔러보고 되는 조합을 골라 쓴다. 네 번이라
몇 초면 끝난다. 어느 게 맞는지 추측하며 하나씩 고치는 것보다 빠르다.

**응답이 XML이 아닐 때가 있다.** 키가 틀리면 XML 대신 HTML 에러 페이지가
온다. 그대로 파싱하면 원인을 알 수 없는 예외가 나므로, 파싱에 실패하면
응답 앞부분을 찍어준다.

**에러코드를 읽어준다.** 기술문서의 코드표를 `ERROR_MSG`에 옮겨두었다.
자주 보게 되는 것은 20번(활용승인 전), 22번(일일 트래픽 초과),
30번(등록되지 않은 서비스키)이다. 403은 다음 달에도 똑같이 실패하므로
즉시 중단한다. 그대로 두면 180번을 헛돌며 화면만 채운다.

**한 달치가 한 페이지에 다 안 온다.** `totalCount`와 비교하며 끝까지
받아야 누락이 없다. 한 페이지로 충분하겠거니 하면 데이터가 조용히 새고,
에러가 나지 않으니 한참 뒤에나 알아챈다.

**구 API와 신 API의 컬럼명이 다르다.** `aptname`↔`aptNm`,
`reqgbn`↔`dealingGbn`, `rdealerlawdnm`↔`estateAgentSggNm` 같은 식이다.
`pick()`이 후보를 여럿 받아 실제 있는 것을 고른다. 한쪽만 박아두면 어느
날 그 컬럼이 통째로 비는데, 에러가 안 나서 알아채기 어렵다.

**해제된 거래는 뺀다.** `cdealType`이 `O`인 건이다. 남겨두면 거래량이
부풀고, 신고가를 찍고 취소한 건이 가격을 위로 끌어올린다.

**API는 기간 조회를 지원하지 않는다.** `DEAL_YMD`가 6자리라 한 번에 한
달치만 준다. 조회할 월을 전부 나열해 반복해야 한다.

## 이 자료로 알 수 없는 것

실거래 신고자료에는 거래 사실만 들어 있다. 왜 그렇게 거래됐는지는 없다.
그래서 코드도 주석도 관측값의 원인을 단정하지 않는다.

이전 판에는 정비사업 단계나 규제 해당 여부 같은 외부 정보로 거래를
분류하는 기능이 있었는데 v7에서 걷어냈다. 분류 기준이 분석 결론을 미리
정해버리는 문제가 있었다. 그런 분류는 이 자료가 아니라 별도 조사의
몫이다.

`연간_시장규모_억` 컬럼은 거래량에 중개보수 상한요율을 곱한 어림값이다.
상한이고 협의 결과가 아니므로 실제 금액과는 다르다.

## 인증키

**키를 파일에 적지 않는다.** 환경변수로만 넘긴다. 한 번이라도 커밋되면
기록에서 지워도 남는다. 실수했다면 파일을 고치는 것으로 끝내지 말고
공공데이터포털에서 키를 재발급받는다.

수집한 CSV도 저장소에 넣지 않는다(`.gitignore`). 공개 자료라 비밀은
아니지만 코드를 돌리면 다시 만들어지고, 넣으면 용량만 커지고 diff가
읽히지 않는다.
